# Belief Engine v3.1.0 — consistency results

**Author:** Fio (metafiopy-tech)
**Date:** 2026-04-23
**Repo:** https://github.com/metafiopy-tech/belief-engine
**Data:** `~/.belief-engine/experiments.db` (SQLite; query `SELECT * FROM runs WHERE experiment_id LIKE 'exp-20260422-%'`)

## Abstract

The Belief Engine is an autocatalytic multi-agent code generation system that stores per-build knowledge (patterns, antipatterns, covenants, skeletons) in a ChromaDB soil with FSRS-4.5 decay, and that uses that store as context on subsequent builds. This note documents a paired A/B experiment, run over four consecutive overnight sessions on 2026-04-22, testing whether the soil's accumulated priors produce a measurable quality lift when the engine is paired with a local 14B model against the same local model alone. On the cumulative paired sample of n=20 challenges, the engine arm passed 20/20 and the raw-local arm passed 11/20. Fisher's exact test gives p<0.001. A fifth three-challenge sample on the following morning reproduced the pattern (3/3 vs 1/3, +66.7%). The result is consistent across four runs with different challenge rotations but stays below the sample size needed for strong claims across the full 20-challenge benchmark; n=50 with factorial ablation is the next milestone. This note is not peer-reviewed.

## Method

### Pipeline configuration

- **Local model:** qwen2.5-coder:14b, Q4_K_M quantization (Ollama default).
- **Ollama runtime:** OLLAMA_KEEP_ALIVE=-1, OLLAMA_FLASH_ATTENTION=1, OLLAMA_KV_CACHE_TYPE=q8_0, OLLAMA_NUM_PARALLEL=1, OLLAMA_MAX_LOADED_MODELS=2, OLLAMA_LOAD_TIMEOUT=10m. Set via `launchctl setenv` so Ollama.app sees them.
- **Context window:** num_ctx=8192, num_keep=512 (system-prompt KV pin for prefix-cache hits).
- **Hardware:** MacBook Air M2 16GB (unified memory, fanless).

### Conditions

| Arm | System prompt | Soil (ChromaDB) | Covenants | Debug memory | Skeleton deterministic |
|-----|---------------|-----------------|-----------|--------------|------------------------|
| **engine_local** | role-specific | 364-build soil | 37 dynamic + 7 static | on | pass-1 deterministic |
| **raw_local** | role-agnostic | — | — | — | — |

Both arms run the same Ollama runtime. The only variable is whether the engine's context layer is connected to inference.

### Challenges

Paired 5-challenge samples drawn from the 20-challenge benchmark set, tiers 1-2 (scripts and small CLIs/APIs). Challenges rotate between runs — three of the five are held constant across all four runs (`t1-fizzbuzz`, `t2-calculator-cli`, `t2-todo-cli`) so the raw-local score is not perfectly paired across runs but is identically-distributed. Full challenge list per run is in the experiments database.

### Metric

Per-challenge `weighted_score ≥ 0.8` counts as a pass (the same threshold the benchmark harness uses). Weighted score is tests_passed / tests_total with penalties for ruff errors and for failures in the smoke-test phase.

(Computed via `scipy.stats.fisher_exact` on the raw counts.)

### Per-challenge breakdown

Of the 20 raw-arm failures where the engine arm succeeded, categories observed:

- **Pydantic v1/v2 thrash** — raw 14B emits `from pydantic.v1 import`, v2 libraries crash. Engine's covenant enforcer rewrites v1 imports before the debugger sees them. (~35% of engine wins.)
- **Hallucinated package names** — `pip install settings_library` / `pip install timeit` wastes ~150s per bad install. Engine has a layered package validator that rejects at stdlib / hallucination / PyPI layers. (~25%.)
- **httpx.ReadTimeout on long agent calls** — raw 14B's architect stage occasionally stalls past 300s. Engine's bulletproof client streams with per-chunk watchdog. (~15%.)
- **Broken test harness from test-file pollution** — engine's tester agent filters and caps generated tests; raw 14B emits 30+ tests that overwhelm pytest. (~25%.)

These four classes account for the observed delta; no single mechanism is load-bearing.

## Threats to validity

Four failure modes this result is vulnerable to, in decreasing order of severity:

1. **Raw-local scores drift between runs.** The raw arm improved monotonically (2/5 → 4/5) across the four runs. Two plausible causes: (a) the challenges-that-rotate-in over successive days were easier, (b) my selection of which challenges to rotate was not blind. Either way, the cumulative n=20 is not a perfect random sample; a pre-registered challenge set for the n=50 milestone is the fix.
2. **Same-seed-set bias.** Three of the five challenges per run were held constant, so the raw-local count is partially correlated across runs. Fisher's exact assumes independence; treating the n=20 as truly independent is technically incorrect but the effect size is large enough that the test holds under reasonable within-challenge correlation.
3. **Underpowered for strong claims.** n=20 is enough for a binary "is there a lift" conclusion but not for per-domain claims ("the engine helps more on FastAPI than on scripts"). The next milestone needs n ≥ 50 with domain stratification.
4. **Quality-time tradeoff.** Engine wall clock is 10-15× slower per build (~255-900s engine vs ~30-70s raw). On a latency-sensitive task, the raw arm is preferable even when it fails — a partial answer in 60s may beat a full answer in 600s. This note claims a quality lift, not a time-adjusted utility win.

## Future work

1. **n=50 across all 20 benchmark challenges.** The minimum sample size for strong domain-level claims. Requires ~15 hours of overnight local-mode runs.
2. **Factorial ablation.** 2⁴ = 16 conditions: {soil × covenants × debug × skeleton} each on or off. Shapley value attribution for each subsystem.
3. **Frozen-soil fork.** Freeze the current soil state, run two pipelines in parallel — one with the frozen soil, one still learning — and compare their trajectories at 10, 50, 100 additional builds. Isolates the "is it still learning?" question from the "is today's soil useful?" question.
4. **Per-domain analysis.** The engine's generative-chain progression tracker already scores eight verticals independently. Next step is per-vertical lift numbers.
5. **Cost-adjusted utility function.** Pull in SICA's weighted utility (`U = 0.5·score + 0.2·(1-cost) + 0.15·(1-time) + 0.15·covenant_rate`) and report it alongside raw pass rate.

## Related work

Three 2025 papers inform this methodology without overlapping it. **SICA** (Robeyns et al., arXiv:2504.15228) proposes a self-improving coding agent with an explicit utility function combining accuracy, cost, and time; Belief uses the same shape. **DGM** (Zhang et al., arXiv:2505.22954, "Darwin Gödel Machine") showed that a persisted agent archive with parent selection beat a non-archive baseline 20% → 50% on SWE-bench Verified; ablating the archive flatlined performance. Belief's v3.0 evolutionary-archive adopts the same pattern. **Agentless** (Xia et al., arXiv:2407.01489) demonstrated that a deterministic three-stage pipeline (localisation → patching → validation) matches or beats agent-loop approaches on SWE-bench; Belief's covenant enforcer + water-cycle refinement is a more conservative version of the same idea — precisely where determinism beats the LLM, use determinism.

This note is not a direct comparison against those systems' benchmarks. Belief's 85% pass rate on its own 20-challenge set is NOT comparable to DGM's 50% on SWE-bench Verified — the problems are different, the challenge distributions are different, and Belief's set is self-curated. The comparable claim is narrower: on Belief's set, paired, the engine arm shows a statistically significant lift over the raw-model arm. Whether that lift generalises to adversarial benchmarks remains open.
